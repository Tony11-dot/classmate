## Your 3 actions

**1. Create the QA sandbox (2 min).** From the repo root:

```bash
bash docs/qa/setup-qa-school.sh
```

It asks for your owner (manager) password, then creates the QA school, its admin (`qa.admin.cm`), teacher, 2 students in "QA Class 10-A", and a linked parent — verifies the logins — and writes `docs/qa/QA-CREDENTIALS.txt`. ⚠ I attempted the owner login during setup and it was rejected, so the owner password I had on record may be outdated — the script will tell you immediately if the login fails (mind the 5-attempts-per-15-min limit).

**2. iOS — TestFlight public link (5 min + Apple's ~1-day beta review, once).**
App Store Connect → your app → TestFlight → **External Testing** → create group "QA Testers" → add build 1.0.9 (233) → enable **public link**. First external build triggers a lightweight Beta App Review (~24 h). That public link is what you paste to all testers. (Fallback if you don't want to wait: release 1.0.9 to the App Store first and let testers use the store app.)

**3. Android — register tester Gmails (1 min per tester).**
Play Console → Testing → the track that has build 233 → **Testers** → add their Gmail addresses → they open the opt-in link above, accept, and install from Play.

## Notes & decisions made for you

- Testers log in with **username** — no emails needed, no deliverability issues. Password-reset testing uses a real email the admin sets on a user (covered in checklist AUTH-08).
- The QA school is fully isolated (all reads are school-scoped) — testers can't touch real data; still, credentials are gitignored and should be rotated/school-deleted (Manager console → delete QA school) after the round.
- Giving testers the **admin** account is deliberate: admin user-creation is itself on the checklist (ADM-01..09), and it lets them self-serve extra accounts.
- Web build and billing are out of scope this round; manager console is unreachable for testers by design.
